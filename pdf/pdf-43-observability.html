Part 01

👁️ What is Observability? — The Four Pillars

🟢 5 MIN

Observability is the ability to understand what is happening inside a system by examining the data it produces — without having to ship new code to ask a new question. It relies on four core pillars:

TASK [The Four Pillars]and the question each answers
📜
Logs
"What happened, and what did it say?"

Discrete, timestamped records of events — the error, the warning, the startup message.

📈
Metrics
"How much, how fast, how often?"

Numeric measurements over time — CPU, requests per second, response latency.

🔗
Traces
"Where did the time go?"

The full path a single request takes as it moves across the different services.

📊
Visualization
"Can a human act on this?"

Turns raw signals into dashboards a human can read and act upon.

The first three pillars produce and store the signals — the fourth makes them understandable and actionable.

KEY IDEAThe pillars don't overlap — each answers a different kind of question: a Log tells you what happened in detail, a Metric tells you how much and how fast, a Trace tells you where the time went. A full investigation uses all three together.
NOTE · Why the definition mattersNotice the key phrase: "without shipping new code to ask a new question." You instrument the system once; after that, any new question ("why was latency high at 2 AM?", "which pod threw the error?") is answered by querying data that already exists — not by redeploying with extra print statements. A good observability system answers questions you didn't anticipate when you built it — unlike traditional monitoring, which only answers pre-written questions.
🎓 EXAMThe classic interview opener: "What is Observability, and what are its pillars?" → Understanding system state from its data without deploying new code · Pillars: Logs · Metrics · Traces · Visualization — with the question each one answers.

Part 03 · Logs 1/3

📜 Why Loki? — The Philosophy & the Differences

🟡 6 MIN

Loki is a horizontally-scalable, multi-tenant log aggregation system built by Grafana Labs. It stands apart from full-text systems like ELK for four essential reasons:

💰 Cost-Effective — the cheapest

10–20× cheaper for storage, because Loki indexes only metadata (labels) — not the full text of every log line. Light indexing = light storage bill.

🗄️ Storage — cheap tiers

Logs are compressed into chunks and stored in cheap object storage (or a local filesystem in labs) — no massive search nodes needed.

🔍 Querying — LogQL

You query Loki with LogQL — a language deliberately designed to be similar to PromQL. Learn one and the other feels familiar.

🔗 Integration — native fit

Native Grafana integration (no separate UI needed), and it uses the exact same label model as Kubernetes and Prometheus.

TASK [Loki vs ELK — the difference in one line]the trade-off
ELK: indexes full text → powerful text search 💪 ⇄ Loki: indexes labels only → 10–20× cheaper 💰
KEY IDEA · The mental model + the philosophyThink of Loki as "Prometheus for logs." And the philosophy in one line: "don't index what you won't query." Indexing metadata (which namespace? which pod? which container?) is enough to filter millions of lines, leaving the raw text to be read only at query time — that's the root cause of both its cheapness and its query behavior: label selectors are fast, line filters are done on the fly.
WATCH OUTThe trade-off is real: because Loki doesn't index the log text itself, free-form full-text search is weaker than ELK. You query by labels first, then narrow with LogQL. In Kubernetes environments with good labels — exactly our case — the trade-off pays off enormously.
🎓 EXAMThe four reasons: Cost (10–20× cheaper — labels-only indexing) · Storage (chunks in cheap object storage) · LogQL (similar to PromQL) · native Grafana integration + same label model. Mental model: "Prometheus for logs" · Philosophy: "don't index what you won't query."

3-AThe five-stage pipeline

Logs travel through Loki's architecture along a specific path — writes flow down the pipeline, reads come back from the Store:

1️⃣ Promtailships from the nodes
──►
2️⃣ Distributorvalidates & hashes streams
──►
3️⃣ Ingesterbatches into chunks, writes
▼
4️⃣ Storechunks + index (object storage / disk)
◄──
5️⃣ Querierexecutes LogQL from Grafana

WRITE: container log files → Promtail → Distributor → Ingester → Store  ·  READ: Grafana —LogQL→ Querier → reads chunks + index from Store/Ingester

ComponentJob
1. PromtailShips logs from the nodes
2. DistributorValidates and hashes the incoming log streams
3. IngesterBatches the streams into chunks and writes them
4. StoreStores the chunks and the index (object storage or local disk)
5. QuerierExecutes the LogQL queries coming from Grafana
KEY IDEAA log stream = a unique combination of labels. Every distinct label set is its own stream — which is exactly why the labels Promtail attaches matter so much (Part 3·c).
NOTE · Reads vs writesWrites flow left→right down the pipeline (1→4). Reads never touch the write path's front: the Querier (5) pulls already-stored chunks + index from the Store (and Ingester for recent, not-yet-flushed data).
🎓 EXAMThe pipeline: Promtail → Distributor (validates & hashes) → Ingester (chunks) → Store (chunks + index) ← Querier (LogQL). A log stream = a unique label combination.

Part 03·c · Logs 3/3

🚚 Promtail Workflow — Why a DaemonSet + the 4 Steps

🟡 6 MIN

Promtail runs as a DaemonSet — one pod per Kubernetes node. Why? Because container logs are files on each node's local filesystem. A Promtail pod on node A physically cannot read node B's /var/log/pods. Node-local data ⇒ node-local collector.

TASK [The four steps]discover → tail → label → ship

1️⃣ Discover

Uses Kubernetes service discovery to find every pod running on its node.

2️⃣ Tail

Reads container log files directly from /var/log/pods — like a tail -f.

3️⃣ Label

Attaches K8s metadata as labels: namespace, pod, container, node.

4️⃣ Ship

Batches log lines and pushes to Loki's distributor over HTTP.

KEY IDEA · Labels are the gear in the machineStep 3 matters more than it looks: because Promtail's labels are identical to Prometheus's labels, switching between logs and metrics in Grafana is seamless — same namespace, same pod, same language — and logs and metrics are cross-correlatable by default. See a CPU spike on pod X, namespace Y in a Prometheus panel → query {namespace="Y", pod="X"} in Loki → read the logs from exactly that window. Zero extra configuration produces this.
WATCH OUT · Label cardinalityLabels are indexed, so they're relatively expensive in Loki — never attach unbounded varying values (like user_id) as labels. Keep it to stable, structured ones: namespace, app, pod, container, node.
NOTEStep 4 completes the push model: Promtail pushes batches over HTTP — the opposite of Prometheus, which pulls from targets. Same labels, opposite transport direction.
🎓 EXAMPromtail = DaemonSet (one pod per node — logs are node-local files in /var/log/pods) · Steps: Discover → Tail → Label (same K8s labels as Prometheus) → Ship (HTTP push) · Shared labels = free log↔metric correlation.

Part 04 · Metrics 1/2

📈 Prometheus — Fundamentals

🟡 6 MIN

Prometheus is an open-source monitoring system that uses a pull model: it scrapes metrics from targets on a regular interval, rather than waiting for applications to push data.

TASK [The three core concepts]storage · querying · alerting

🗄️ Storage

Every measurement is a Time Series: a metric name + key/value labels + a sequence of timestamped values. Example: container_cpu_usage_seconds_total{namespace="app", pod="api-7d9f"} — labels are the dimensions you aggregate by.

🔍 Querying — PromQL

A powerful query language for aggregating, filtering, and computing rates over time series.

🚨 Alerting — Alertmanager

Pairs with Alertmanager to turn PromQL conditions into routed alerts — Slack, Email, PagerDuty. (Disabled in this lab — but the concept stands.)

TASK [Why pulling matters]practical consequences
CENTRAL CONTROLThe Pull Model gives Prometheus full control: it knows when the last scrape happened and decides the cadence and the target list — apps don't need to know where Prometheus lives. Just expose a /metrics endpoint, nothing more.
FAILURE IS VISIBLEA dead target doesn't just leave a gap in the data — its up metric goes to 0. A target that won't respond to a scrape = down. You can literally query whether monitoring works.
TASK [Service discovery]no manual IP lists
In Kubernetes, Prometheus automatically finds targets via service discovery + Custom Resources (CRDs)

Nobody maintains a list of pod IPs — pods are ephemeral anyway; the list would be stale in minutes.

WATCH OUTEvery unique combination of labels creates a new series — the same label-explosion issue as Loki: too many varying labels = an explosion in series count.
🎓 EXAMPrometheus: Pull Model · Time series = name + labels + timestamped values · Querying: PromQL · Alerting: Alertmanager (disabled here) · Target discovery: automatic via service discovery + CRDs · Dead target = up == 0.

Part 05

🔗 Traces — The Journey of a Request

🟢 4 MIN

A trace records the full journey of a single request as it moves through multiple services:

TASK [The journey of one request]a worked example
🌐 API Gateway 2ms ──► 🔐 Auth Service 15ms ──► 📦 Order Service 40ms ──► 🗄️ DB Query 120ms ⚠

The trace reveals instantly: most of the time went to the DB Query — no guessing, no manually checking every service.

5.1The purpose

Traces show exactly where time was spent during a request. Metrics tell you that requests are slow; traces tell you which hop made them slow — which service was slow, which call repeated, where the real bottleneck lives.

5.2The tools

Tracing typically uses Grafana Tempo, Jaeger, or Zipkin, with applications instrumented via OpenTelemetry.

NOTE · In this labTraces are not deployed in this specific lab — but they represent the natural next step once logs (Loki) and metrics (Prometheus) are in place. Two of the three signals are already running.
KEY IDEAWhen someone tells you "the API is slow" — Logs tell you what happened, Metrics tell you how slow, but only the Trace tells you exactly where inside the request journey the time went.
🎓 EXAMA Trace = the journey of one request across multiple services · Purpose: where the time was spent · Tools: Grafana Tempo / Jaeger / Zipkin via OpenTelemetry · not deployed in this lab — the next step.

Part 06

📊 Grafana — The Unified UI

🟡 7 MIN

Grafana is the unified UI for observability — the pane of glass where logs and metrics meet.

TASK [Four concepts]data · config · dashboards · explore

🔌 Data Handling

Grafana does not store data itself — it connects to Data Sources (Prometheus, Loki) and queries them live on every panel refresh. Wipe the backends and Grafana has nothing to show — it's a lens, not a database.

⚙️ Configuration

Each Data Source requires: a URL + authentication + the query language it should speak (PromQL or LogQL).

📊 Dashboards & Panels

A Dashboard is a collection of Panels. Each panel runs a query and renders it as a graph, table, log stream, or gauge. Dashboards are JSON — version-controlled, or imported from grafana.com/dashboards by numeric ID.

🔍 Explore Mode

Run ad-hoc PromQL or LogQL queries without building a dashboard — the go-to tool for debugging ("just show me the errors from that namespace right now").

TASK [The hierarchy inside Grafana]the hierarchy
📊 Dashboard ◂ contains 🧩 Panels ◄ query from 🔌 Data Source ◄ which is 🗄️ Loki / 📈 Prometheus
KEY IDEAGrafana is deliberately memoryless: every panel = a live query at the moment of viewing. Nobody asks "is the dashboard up to date?" — it's up to date by definition, because it queries the source directly on every load.
✅ EXPLOIT THIS · Dashboards as codeDashboards are JSON — commit them to Git. A lost dashboard = restore from Git; an intentional change = a Pull Request reviewed like any other code. Version-controlling dashboards is a feature to exploit, not an accident.
WATCH OUT · Deployment detailIn this stack, Grafana is installed by kube-prometheus-stack, not deployed standalone. That fact is exactly what causes the datasource conflict in Part 8·b — the single best "bug I debugged" story in this guide.
🎓 EXAMGrafana: stores nothing — live Data Sources · Data Source = URL + Auth + Query Language · Dashboard = set of Panels (graph/table/logs/gauge) · Dashboards = JSON → Git: restore + PR review · Explore = ad-hoc debugging.

Part 07

🧩 How It All Fits Together — in Kubernetes

🟡 6 MIN
TASK [The complete data flow]six steps, end to end
  1. Application pods write logs and (optionally) expose /metrics.
  2. On every node, Promtail (DaemonSet) tails /var/log/pods, labels each line with Kubernetes metadata, and pushes batches to Loki's distributor.
  3. On every node, node-exporter (DaemonSet) exposes host metrics; cAdvisor (in the kubelet) exposes per-container metrics; kube-state-metrics exposes object state.
  4. Prometheus pulls all of those metrics on a scrape interval, discovering targets via Kubernetes service discovery and CRDs (ServiceMonitor/PodMonitor).
  5. Grafana holds both as data sources and queries Prometheus (PromQL) and Loki (LogQL) live.
  6. You open Grafana in a browser through a port-forward tunnel and see everything.
TASK [Two transports, one label model]the glue
📜 Promtail ── pushes logs (HTTP) ──► 🗄️ Loki
📈 Prometheus ◄── pulls metrics (scrape) ── 🖥️ node-exporter · cAdvisor · kube-state-metrics · apps

But both carry the same labels — namespace / pod / container / node — which is what makes the stack feel like one system.

KEY IDEALogs are pushed; metrics are pulled. The transport directions differ, but the label vocabulary is identical — that shared label model is the glue. It's why one label pivot in Grafana jumps you from a CPU graph to the exact log lines that explain it.
NOTE · Access patternGrafana is a ClusterIP Service — reachable only from inside the cluster. From your laptop you reach it via kubectl port-forward (full command + decode in Part 8·b).
🎓 EXAMFlow: apps/nodes produce → Promtail pushes logs → Loki · Prometheus pulls metrics → TSDB · Grafana queries both live → browser via port-forward. Push ≠ Pull, but labels are shared.

Part 08 · Deployment 1/2

🚀 Helm + kube-prometheus-stack

🟠 8 MIN

Helm is a package manager for Kubernetes. It bundles all necessary manifests — Deployments, Services, ConfigMaps, CRDs — into "charts." Installing a chart creates a release. Charts live in repositories you add to your host. Instead of dozens of hand-written YAML files, two Helm commands deploy the entire platform — including default dashboards and wired-up data sources. Helm turned a week-long project into two commands.

TASK [Setup — repos + namespace]best practice: dedicated namespace
# add both chart repositories, refresh indexes, create the namespace helm repo add prometheus-community https://prometheus-community.github.io/helm-charts helm repo add grafana https://grafana.github.io/helm-charts helm repo update kubectl create namespace observability # keeps monitoring separate from app workloads
TASK [Chart 1: kube-prometheus-stack]one chart, many components
INSTALLSPrometheus · Alertmanager · Grafana · node-exporter · kube-state-metrics · ServiceMonitor/PodMonitor CRDs · default Kubernetes dashboards — in one shot.
⚠ RESOURCE MANAGEMENTBy default this chart requests more CPU and RAM than a small Minikube cluster can handle — install it bare and pods sit in Pending because the scheduler can't fit their requests anywhere. You must drastically trim resource requests and limits for every component with --set flags:
helm upgrade --install kube-prometheus-stack prometheus-community/kube-prometheus-stack \ -n observability \ --set alertmanager.enabled=false \ --set prometheus.prometheusSpec.retention=6h \ --set grafana.adminPassword=admin123 \ --set prometheus.prometheusSpec.resources.requests.cpu=100m \ --set prometheus.prometheusSpec.resources.requests.memory=256Mi \ --set grafana.resources.requests.cpu=50m \ --set grafana.resources.requests.memory=128Mi # ...similar trimming for kube-state-metrics & node-exporter. # Exact value keys: helm show values prometheus-community/kube-prometheus-stack
OverrideWhy
Resources trimmed (every component)Chart defaults assume beefy nodes; Minikube pods go Pending otherwise
retention=6hTSDB storage grows with retention; a lab needs no history — 6h is plenty for debugging

TASK [⚠ The datasource provisioning conflict]the one non-obvious gotcha
  1. loki-stack ships its own Grafana data-source ConfigMap for Loki.
  2. The Grafana sidecar (in the Grafana installed by kube-prometheus-stack) auto-discovers datasource ConfigMaps and loads them — Loki appears with zero manual config. Nice.

🔍 LogQL — Querying Loki

🟡 7 MIN

Framing: two backends, two query languages, one UI. LogQL was deliberately designed to be similar to PromQL, and both select by the same labels — learn one, and the other feels familiar.

TASK [Start in Explore mode]no dashboard needed
Grafana → Explore → pick datasource → run ad-hoc queries
🗄️ Loki: {namespace="observability"} → live streams 📈 Prometheus: up → 1 = healthy, 0 = down
TASK [LogQL — every query has up to three stages]selector → pipeline → wrapper

1️⃣ Stream selector

Labels — indexed, fast. Picks which log streams to read.

2️⃣ Filter pipeline

Line filters — evaluated at query time on the matched streams.

3️⃣ Metric wrapper

Turns log counts into numbers — logs become a metric.

# 1) Stream selector: all logs from a namespace {namespace="observability"} # narrow by pod / container (the labels Promtail attached) {namespace="default", pod="my-app-7d9f8b6c-", container="app"} # 2) Line filters: keep / drop lines by content (Loki searches text HERE) {namespace="observability"} |= "error" {namespace="observability"} |= "error" != "timeout" # 3) Metric query: count matching log lines per pod over a 5m window sum by (pod) (count_over_time({namespace="default"} |= "error" [5m]))
KEY IDEA · Why this ordering mattersThe label selector runs against the index; the text search runs against the matching streams at query time. That's the direct payoff of Loki's "index only labels" design — cheap storage doesn't mean slow queries if your labels are chosen well.
NOTE · The bridgeStage 3 converts logs into a metric (count_over_time over a [5m] range) — structurally a sibling of PromQL's rate(), and the bridge between the two signal types.
🎓 EXAMLogQL = stream selector (indexed) → line filters (query-time) → optional metric wrapper · |= keep, != drop · count_over_time(...[5m]) turns error lines into a per-pod rate.

📈 PromQL — Querying Prometheus

🟡 6 MIN
TASK [Core examples — annotated by source component]know who exposes each metric
# Health of every scrape target (1 = up, 0 = down) up # Only the observability stack itself up{namespace="observability"} # Per-container CPU rate over 5m — metric from cAdvisor (via kubelet) sum by (pod) (rate(container_cpu_usage_seconds_total[5m])) # Container memory right now — cAdvisor sum by (pod) (container_memory_usage_bytes) # Node memory available, as a fraction — metric from node-exporter node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes
TASK [Two mechanics worth internalizing]range vectors & aggregation

⏱ [5m] = a range vector

Selects many points over 5 minutes — functions like rate() require a range. A single instant value can't produce a rate.

🧮 sum by (pod) = aggregation

Aggregates across labels, keeping pod as the grouping dimension — the same labels Loki uses, so results line up across both backends.

TASK [Instant vs trend debugging]pick the right question
"Right now, is it broken?" → up · raw stream {namespace="..."}
"Trending toward broken?" → rate() over [5m] · errors/pod · memory fraction graphs
KEY IDEABecause both query languages select by the same labels, the same sum by (pod) grouping works on both sides — a per-pod error rate from Loki lines up exactly with a per-pod CPU rate from Prometheus in adjacent Grafana panels.
🎓 EXAMup = scrape health · rate(counter[5m]) needs a range vector · sum by (pod) keeps the grouping label · cAdvisor → container metrics · node-exporter → node_* metrics.

🛠️ Troubleshooting Playbook — Scenarios 1–3

🟠 8 MIN

Reason from symptom → diagnosis → root cause → fix. The diagnostic command sequence matters more than memorizing fixes.

🔴 Scenario 1 — Pods stuck in Pending

Symptomkubectl get pods -n observability → pods sitting in Pending, not starting
Diagnosekubectl describe pod <pod> -n observability → events show FailedScheduling: Insufficient cpu / memory
Root causeCluster lacks free CPU/memory — the chart's default resource requests don't fit on the Minikube node, and the scheduler will not place a pod whose requests don't fit
FixLOWER REQUESTS (the --set overrides from Part 8) or GROW MINIKUBE (--cpus=... --memory=...)
LessonPending = scheduling problem = look at requests vs available before anything else

🔴 Scenario 2 — Grafana OOMKilled

SymptomGrafana restarts repeatedly; kubectl describe pod shows OOMKilled (exit code 137)
Root causeThe container ran out of memory — it exceeded its own memory limit
Diagnose firstCheck the node's free memory first (kubectl top nodes) — do not blindly raise the Grafana limit
FixNode has headroom → RAISE LIMIT via --set; node exhausted → FREE CAPACITY (disable components, trim pods, grow Minikube)
LessonOOMKilled = limit problem; node exhaustion = capacity problem. Diagnose which one you have.

🔴 Scenario 3 — Grafana CrashLoopBackOff with a provisioning error

SymptomGrafana cycles CrashLoopBackOff; logs show "Datasource provisioning error."
Diagnosekubectl logs <grafana-pod> -n observability · kubectl get configmap -n observability → two datasource ConfigMaps, both marked default
Root causeTwo datasources marked default — Grafana permits exactly one; provisioning fails at startup every time → crash loop. Not a resource problem — a config validation failure can crash-loop a perfectly sized pod.
FixPrevent: install loki-stack with defaultDatasourceEnabled=false · Repair: remove isDefault: true from the extra ConfigMap, then kubectl delete pod (Deployment recreates it clean)
LessonRead the crash logs — the error names the subsystem (provisioning), which points straight at ConfigMaps. This is the star interview story.

🟠 Scenario 5 — "Grafana shows no data" (general reasoning flow)

Work the chain in order — the boring causes are the common ones:

  1. Is the backend pod running? → kubectl get pods -n observability (a crashed Loki or Prometheus means no queries can succeed).
  2. Is the datasource alive? → Explore → run up (Prometheus) or {namespace="observability"} (Loki). If Explore works but a dashboard doesn't, the problem is the dashboard's query/time-range — not the stack.
  3. Missing app metrics specifically? → no /metrics endpoint, or the ServiceMonitor selector doesn't match — check up for the target.
  4. Right namespace? Right time range? → always worth a glance.

Part 14 · Interview Prep

🎤 Concept Questions — with Distilled Answers

🟠 10 MIN
Q1 What is observability?
Understanding what's happening inside a system from the data it produces — without shipping new code to ask a new question. Pillars: logs, metrics, traces, visualization.
Q2 Logs vs metrics vs traces — when each?
Logs = what happened (exact events). Metrics = how much/how fast (trends, alerting). Traces = where the time went (per hop). Debug flow: alert → trace → log.
Q3 Why is Loki 10–20× cheaper than full-text systems?
It indexes only metadata (labels), not log text; text is searched at query time. Chunks are compressed into cheap object storage.
Q4 Pull vs push — Prometheus vs Promtail?
Prometheus pulls (scrapes on an interval — central cadence control; dead target visible via up=0). Promtail pushes HTTP batches to Loki's distributor.
Q5 Why are Promtail & node-exporter DaemonSets?
Their data is node-local: container logs live in each node's /var/log/pods; host metrics are per-machine. One pod per node = full coverage.
Q6 What makes up a Prometheus time series?
A metric name + key/value labels + a sequence of timestamped values.
Q7 node-exporter vs kube-state-metrics vs cAdvisor?
Host-level machine metrics (DaemonSet) vs K8s object state from the API server (pod status, replicas, restarts) vs per-container usage built into the kubelet.
Q8 What are ServiceMonitor/PodMonitor and why?
CRDs that declaratively tell Prometheus which Services/Pods to scrape — no manual IP lists; deploying the CRD is the config (Helm auto-wires it).
Q10 Why helm upgrade --install over helm install?
Idempotency — re-running upgrades an existing release in place instead of failing.
Q11 Why port-forward instead of NodePort/LoadBalancer?
Grafana is ClusterIP (internal only). Port-forward = zero-config lab access; NodePort/LB/Ingress expose it properly. On Windows/WSL you must pass --address 0.0.0.0.
Q12 Why drop Prometheus retention to 6h in a lab?
TSDB storage grows with retention; a lab needs no history — 6h saves significant disk.
Q13 How do logs and metrics link in this stack?
Same label model — Promtail attaches the exact labels Prometheus uses (namespace/pod/container/node), so a metric anomaly maps directly to that pod's log stream.
Q14 Natural next step for this stack?
Traces — deploy Grafana Tempo (or Jaeger/Zipkin), instrument apps with OpenTelemetry — completing all three signals.
Q9 ⭐ Tell me about a bug you debugged in this stack.
Grafana CrashLoopBackOff with a datasource provisioning error: both charts provisioned a datasource marked default; Grafana allows exactly one. Diagnosed via pod logs + kubectl get configmap; fixed by grafana.sidecar.datasources.defaultDatasourceEnabled=false (or removing isDefault: true).
🎓 INTERVIEW TIPQ9 is the star story — it shows real debugging: read the crash log, form a hypothesis from the error's named subsystem (provisioning), verify with ConfigMaps, apply the targeted fix, and state the lesson (a config validation failure can crash-loop a perfectly sized pod).
