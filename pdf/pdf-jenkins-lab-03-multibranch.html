CI/CD SYSTEMS MULTIBRANCH PIPELINES

01 / Multibranch Foundations

A standard pipeline executes a single predefined script. A Multibranch Pipeline is structurally different: it is a folder of individual pipeline jobs, one per discovered branch. Jenkins scans the repository, finds branches, and looks for a Jenkinsfile to build with.

01 SCAN REPO Periodic or manual PASSED
02 DISCOVER Filter: main dev stg PASSED
03 JENKINSFILE Locate in branch root RUNNING
04 EXECUTE Create sub-job WAITING
05 ORPHAN Cleanup deleted SKIPPED

WHAT

A Jenkins job type that automatically creates a sub-job for every branch in a Git repository containing a Jenkinsfile.

WHY

It eliminates the need to manually create and configure a new Jenkins job every time a developer creates a new branch.

WHEN

On a periodic schedule (e.g., every 5 minutes) or manually triggered. This task deliberately ignores webhooks to simulate an air-gapped environment.

WHAT CHANGES

The relationship between source code and CI inverts. The repository defines the jobs, not Jenkins. Branch deletion leads to job orphaning.

WHY THIS EXISTS

In dynamic environments with feature branches, manually managing Jenkins jobs is impossible. Multibranch pipelines push job creation down into the repository itself, making the CI configuration version-controlled and branch-specific.

03 / Discovery & Filtering

Configure the Multibranch Pipeline job to use a plain Git source. Filter discovery to exactly three branches: main, dev, and stg. Since no webhooks are used, rely on periodic scanning.

Branch Source Configuration

Jenkins -> New Item -> Multibranch Pipeline > Branch Source: Git (Plain Git, not GitHub) > Project Repository: https://github.com/user/repo.git > Behaviors -> Filter by name (with wildcards) > Include: main dev stg > Exclude: (blank) > Additional Behaviors: > - Check out to matching local branch > - Clean before/after checkout > Scan Multibranch Pipeline Triggers: Every 5 minutes

GOTCHA

Ensure "Check out to matching local branch" is enabled. Without it, Jenkins checks out a detached commit. While builds may succeed, Git metadata within the pipeline won't reflect the actual branch name, breaking when { branch 'stg' } conditionals.

04 / Conditional Execution

A single shared Jenkinsfile must adapt its behavior based on the branch it is building. The env.BRANCH_NAME variable, injected by the Multibranch plugin, enables this via when conditionals.

pipeline { agent any stages { stage('Build') { steps { echo 'Building...' } } stage('Staging Verification') { when { expression { return env.BRANCH_NAME == 'stg' } } steps { sh 'cat README.md' } } } }

Staging Verification (SKIPPED by when)

Build
Staging Verification (SKIPPED by when)

Staging Verification (cat README.md)

INTERVIEW CHECK

Q: How does a single Jenkinsfile adapt to different branches?

A: The Multibranch plugin injects env.BRANCH_NAME. The when directive evaluates this variable before executing a stage, allowing branch-specific logic (like deployment or extra tests) to reside safely in the same file.

CI/CD SYSTEMS LAB: LIFECYCLE MANAGEMENT

05 / Lab: Orphan Cleanup

Branches are not permanent. When a branch is deleted upstream in Git, the corresponding Jenkins job must be removed to prevent clutter. This process does not happen instantly; it requires a scan.

OBSERVE

A feature branch test-branch was merged and deleted from the remote Git repository. The Jenkins folder still shows the job.

EXECUTE

Trigger a manual scan ("Scan Multibranch Pipeline Now") or wait for the periodic scan to execute.

VERIFY

Check the scan log. It will report test-branch as an orphaned item. The job will be removed from the Jenkins folder view.

PROOF

Jenkins state perfectly mirrors the Git repository state. No stale jobs remain.

Folder State Transition

📁 multibranch-job SCANNED
├── main ACTIVE
├── dev ACTIVE
├── stg ACTIVE
└── test-branch ORPHANED

GOTCHA

Orphaned branch cleanup only happens after a rescan. Deleting a remote branch does not immediately remove its Jenkins job. The next scan evaluates the repository state and removes orphaned items.

INTERVIEW CHECK

Q: Why use plain Git branch source instead of GitHub-specific integration?

A: The plain Git source works with any Git provider (GitLab, Bitbucket, etc.) and functions in air-gapped environments where inbound webhooks are blocked. It relies on periodic polling, prioritizing compatibility over immediate trigger speed.
