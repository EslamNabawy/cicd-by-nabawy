CI/CD LABS LAB 07: SHARED LIBRARY

01 / Pipeline Code Reuse

As pipeline complexity grows, duplicating Groovy logic across dozens of Jenkinsfiles creates a maintenance nightmare. Extract a duplicated pipeline step into a versioned shared library consumed by multiple pipelines, achieving reuse without copy-paste.

01 EXTRACT Isolate logic PASSED
02 VERSION Git repository PASSED
03 REGISTER Jenkins global config RUNNING
04 CONSUME @Library annotation WAITING
05 VERIFY DRY payoff WAITING

OBJECTIVE

Move a shared step into a standalone Git repository, configure Jenkins to use it as a Global Pipeline Library, and call it from two distinct pipelines.

ARCHITECTURE

Library repo (vars/standardTest.groovy) → Jenkins Global Pipeline Libraries → multiple Jenkinsfiles call the same step → one fix propagates to all consumers.

Setup: The Library Repository

Create a repository named pipeline-library. Inside, create a directory named vars and a file standardTest.groovy. This file defines a custom step that can be called by any pipeline.

# File: vars/standardTest.groovy def call(Map cfg = [:]) { sh "\${cfg.cmd ?: 'npm test'}" }

WHY IT MATTERS

Versioned libraries are dependencies. They are pinned, reviewed, and rollback-able. Copy-pasted steps are untrackable; shared libraries bring standard software engineering practices to pipeline code.

CI/CD LABS LIBRARY CONSUMPTION

02 / Registration & Consumption

With the library code in a Git repository, Jenkins must be configured to trust and load it. Once registered, pipelines can import the library using an annotation.

Step 1: Register the Library

Manage Jenkins -> System -> Global Pipeline Libraries > Library Name: my-lib > Default Version: main > Retrieval Method: Modern SCM > Project Repository: https://github.com/user/pipeline-library.git

Step 2: Consume from Two Pipelines

In both Jenkinsfiles, import the library and call the custom step. The _ in the annotation tells Jenkins to import the library but not run any global scripts automatically.

@Library('my-lib') _ pipeline { agent { label 'docker-agent' } stages { stage('Test') { steps { standardTest(cmd: 'npm test') } } } }
  • Both pipelines call the library step successfully.
  • Breaking the library breaks both (proves sharing); reverting fixes both.
  • Library change went through PR review on its own repo.

GOTCHA

If you encounter Library my-lib not found, check two things: the name in the Jenkinsfile matches the Global config exactly, and the default version (e.g., main) exists in the repository.

INTERVIEW CHECK

Q: Why must library changes go through PR review on their own repo?

A: Unreviewed shared code risks propagating a breaking change or security vulnerability to all pipelines simultaneously. A PR review acts as a gatekeeper, ensuring the shared logic is safe before Jenkins consumers pull the new version.

CI/CD LABS LAB 08: BACKUP & RESTORE

04 / Disaster Recovery

Backups are imaginary until tested by restoration. Prove disaster recovery: back up the Jenkins controller's home directory, destroy the controller entirely, restore on fresh infrastructure, and replay a smoke pipeline.

01 RUNNING Controller live PASSED
02 ARCHIVE tar jenkins_home RUNNING
03 DESTROY docker compose down -v DESTROYED
04 RESTORE Extract archive WAITING
05 VERIFY Run smoke test PENDING

OBJECTIVE

Perform an offline backup of JENKINS_HOME, wipe the controller and volumes, restore the archive to a fresh controller, and verify job history and credentials.

OFFLINE BACKUP

An offline backup ensures a consistent snapshot. Copying files while Jenkins is live risks capturing half-written state, leading to corrupted configurations upon restore.

Pre-Flight Check

SETUP

Note one job's last build number and one credential ID. These are the exact artifacts you will verify after the restore operation.

CI/CD LABS BACKUP & RESTORE

05 / The Procedure

Execute the disaster recovery drill. The process involves stopping the container, archiving the volume, wiping the slate clean, and rebuilding from the archive.

Step 1: Back Up

$ docker compose stop jenkins $ docker run --rm -v jenkins-lab_jenkins_home:/data \ -v "$PWD":/out alpine tar czf /out/jenkins-backup.tar.gz -C /data . jenkins-backup.tar.gz created successfully. $ docker compose start jenkins

Step 2: Destroy and Restore

$ docker compose down -v # Wipe EVERYTHING $ docker compose up -d # Fresh controller $ docker compose stop jenkins $ docker run --rm -v jenkins-lab_jenkins_home:/data \ -v "$PWD":/in alpine tar xzf /in/jenkins-backup.tar.gz -C /data $ docker compose start jenkins Restore complete. Jenkins initializing...

Verification Checklist

  • Job list + history identical (check the recorded build number).
  • Credential ID present and usable.
  • Smoke pipeline (from Lab 06) runs green on the restored controller.

GOTCHA

If you restore on a different Jenkins image tag, you may encounter plugin version drift. Always pin the jenkins:lts image digest for both controller and backup to guarantee compatibility. If permission errors occur, ensure the volume is owned by UID 1000 (chown -R 1000:1000).

Q: What is the restore proof?

A: The restore proof is running the Lab 06 smoke pipeline on the restored controller. A green status verifies that the agent connection, job configuration, and execution environment were all recovered successfully from the archive.
