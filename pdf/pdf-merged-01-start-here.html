Continuous Integration

05

3 / What Is Continuous Integration

Developers merge small changes into shared main frequently; every merge triggers an automated build + test + scan. CI answers one question: does this change work?

WHEN — on every push and every pull request. HOW — a pipeline job checks out the exact commit, builds it in a clean environment, and reports green or red back to the branch in minutes.

WHY THIS EXISTS

Without automated integration, a broken change travels for days before anyone discovers it. CI moves that discovery to within minutes of the commit — when the author still remembers what they did.

4 / What happens without CI/CD

  • Long-lived branches → merge hell. Weeks of divergent work collide; untangling takes days.
  • "Works on my machine" releases. Testing one thing, shipping another — every deploy a gamble.
  • Manual testing → bugs reach users. Humans skip steps under pressure.
  • Manual deploys → release fear. Rare, big, traumatic events nobody runs on Friday.
  • No feedback loop. The same bug class ships again and again.

Integration pain is paid minutes per commit with CI/CD, or weeks per release without it.

5 / CI vs Delivery vs Deployment

Human gateNoYes — approvalNo

DO YOU DEPLOY TO PRODUCTION AUTOMATICALLY?
YES → CONTINUOUS DEPLOYMENTEvery passing change ships. Requires progressive delivery + instant rollback.

GOTCHA

A green build does not mean the application works in production. It means only the checks inside that pipeline passed.

13 / The Approval Gate

AUTOMATED build ✓ · test ✓ · scan ✓ · artifact ✓  →  ◌ APPROVAL — a human decision is required  →  PRODUCTION
CONTEXT — PRODUCER & CONSUMER

The build pipeline produces the artifact; the deployment pipeline consumes it; the registry stores it. Lifecycle: build → store → promote → deploy. Anything that breaks this chain — a rebuild, a mutable tag, a skipped gate — voids every check upstream.

Source Control

13

Picking up from Foundations, where a Git push triggered the lifecycle — we now examine the machinery of that trigger: branches isolate work, pull requests gate it, triggers fire pipelines.

01 / What Each Piece Is

Git — distributed version control; every commit is a snapshot with author, message, parent.

Branching — an independent line of work (feature/login) forked from main.

Pull Request — a merge proposal combining human review with automated status checks.

CI Trigger — the event that starts a pipeline: PR opened/updated, push to main, schedule, manual.

02 / Why the Gate Exists

Direct pushes to main bypass review and verification. The branch → PR → CI → merge flow makes every change Reviewed, Tested, and Traceable before it can break the pipeline.

Gates

18

02 / PR Gates & Merge Queues

  • PR gate — required checks + approvals in branch protection. No green, no merge. No admin overrides.
  • Merge queue — serializes merges on busy main: rebase onto latest green, re-verify, land. Kills the green-on-branch-red-on-main race.
  • Linear history — rebase/squash keeps main bisectable: any commit builds and reverts cleanly.

03 / Trunk Discipline

RULES tiny branches, daily merges · flags hide unfinished work, not long branches · main always releasable · whoever breaks it fixes it first · measure merges per dev per week.
  • Long branches → merge hell (WIP limits + flags).
  • Red main normalized → quality collapse (stop-the-line culture).
  • Flaky gates → bypassed checks (quarantine flakes, never disable gates).
Q5 CI practice vs CI pipeline?
Discipline (merge small, verify, fix first) vs machinery (the pipeline that enforces it).
DISCIPLINE DETAILS preflight builds validate diffs before landing on main · rotating build master reverts lingering breakage on large teams · ratcheting gates fail only when warnings or duplication increase.

🎤 Concept Questions — Distilled Answers

REF
Q1 Delivery vs Deployment?
Delivery keeps software production-ready behind an approval; Deployment releases validated changes automatically.
Q2 Why must staging and production share one artifact digest?
Otherwise you tested one binary and shipped another — verification is void.
Q3 Explain the PR as a quality gate.
Human review for design plus automated checks for correctness plus merge policy: green and approved equals mergeable.
Q4 Name the trigger types.
Push, pull request, schedule, manual dispatch, tag or release.
Q5 CI practice vs CI pipeline?
Discipline — merge small, verify, fix first — versus machinery: the pipeline that enforces it.
Q6 What causes merge hell, and what fixes it?
Long-lived divergent branches; trunk-based discipline with tiny daily merges and flags.
Q7 A green build passed. Does the app work in production?
Not necessarily — it means only the checks inside that pipeline passed.
Q8 Trunk-based vs Git Flow?
Trunk: branch to PR to main to deploy, for CD teams. Git Flow: develop plus release branches, for versioned releases.
Q9 ⭐ Tell me about a checkout that broke main. What did you change?
STAR story: red main on a Friday deploy — stopped the line, reverted first, then landed a required check so the class of breakage can never merge again.
