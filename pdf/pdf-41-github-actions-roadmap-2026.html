Why GitHub built a security roadmap

THE ATTACK SURFACE

In 2025–26 a pattern emerged: compromise a trusted Action → execute inside CI → exfiltrate secrets. The roadmap is GitHub's direct answer to three root causes: implicit trust in workflow dependencies, poor execution visibility, and overly broad credential exposure.

THE PATTERN

Every incident follows the same pipeline: a normal-looking workflow pulls an Action at a friendly tag, that Action (or its transitive dependency) is silently retargeted, and secrets flow outward before anyone notices. SHA pinning at the top level only does not close this gap.

Pillars A & B

Dependency locking · Scoped secrets

03 / A — Locking Workflow Dependencies

A new dependencies: section in workflow YAML. Works like go.sum / Cargo.lock — but for Actions. GitHub will resolve and lock direct and transitive Action dependencies via commit SHA + cryptographic hash verification.

name: ci on: pull_request dependencies: # NEW — lockfile for Actions actions/checkout: sha256:abc123… # SHA + hash, verified my-org/composite-action: sha256:def456… # transitive deps locked too jobs: build: runs-on: ubuntu-latest steps: - uses: actions/checkout@abc123 # deterministic, diffable
WHY THIS MATTERS — Today's SHA pinning only covers top-level uses: lines, not what a composite Action calls internally. Locking closes that gap: deterministic execution, visible dependency diffs in PRs, and tamper detection even when a SHA looks correct (hash mismatch fails the run). Paired with immutable releases and stricter publishing rules for maintainers.
BeforeAfter (locking)
ScopeTop-level uses: onlyTransitive closure (composite Actions included)
VerificationSHA equalitySHA + cryptographic hash
PR visibilityNo dependency diffLockfile diff surfaces version drift

04 / B — Scoped Secrets

Secrets will be bindable to a narrower scope instead of flowing broadly by default — and will no longer auto-inherit into reusable workflows.

ScopeSecret is available only when
RepositoryWorkflow runs inside that specific repo
BranchWorkflow runs targeting that branch
EnvironmentJob targets the environment (e.g., production)
Trusted workflowOnly an explicitly approved reusable workflow calls it
# BEFORE — secrets auto-inherit jobs: deploy: uses: org/central-deploy@v2 secrets: inherit # ← broad, implicit # AFTER — explicit per-secret binding jobs: deploy: uses: org/central-deploy@v2 secrets: NPM_TOKEN: ${{ secrets.NPM_TOKEN }} # scoped to trusted workflow + env
PERMISSION CHANGE — Repository write access will no longer automatically grant secret-management rights. That moves to custom/delegated roles (separation of duties). Treat secrets: inherit as deprecated — audit for it now.

Pillars C & D

Policy protections · Data stream & Firewall

05 / C — Policy-Driven Workflow Execution Protections

Extends the existing rulesets framework to centrally govern workflow execution — replacing scattered if: github.actor != 'dependabot[bot]' guards spread across individual workflow files.

Rule typePurposeExample
Actor rulesWho/what can trigger workflowsOnly humans, Dependabot, or a specific GitHub App can fire deploy.yml
Event rulesWhich events can trigger runspush allowed; issue_comment blocked unless from maintainer

DIRECTLY TARGETS "COMMENT-AND-CONTROL"

Untrusted contributors trigger agent/automation workflows via issue or PR comments, injecting instructions into AI-assisted runs. Central policy prevents the trigger from ever reaching the runner — no per-workflow patching needed. Status: Public preview shipped June 18, 2026.

# org-level ruleset (conceptual) ruleset: workflow-execution target: workflows conditions: actor: [human, dependabot[bot], my-deploy-app] event: [push, pull_request, workflow_dispatch] # issue_comment / discussion events require actor allow-list

06 / D — Endpoint Monitoring & Control

Actions data stream — near-real-time telemetry for workflow runs, streamed to Amazon S3 or Azure Event Hub / Data Explorer. Designed for SIEM/SOC consumption.

  • Workflow execution metadata — status, duration, runner type
  • Dependency-resolution detail — which Action resolved to which version
  • Network activity — planned; feeds the firewall policy workflow

Native egress firewall (Layer 7) — runs outside the GitHub-hosted runner VM, so code inside the runner cannot bypass it.

ModeBehaviorUse when
MonitoringLogs all outbound trafficBuilding your allow-list without breakage
EnforcementBlocks requests outside the allow-listAfter allow-list is validated in monitoring
ROLLOUT DESIGN — Two-mode rollout is intentional: run in Monitoring to discover destinations, cut to Enforcement only when vetted. This is how GitHub avoids "enforcement day breaks every CI" — mirror the same staged adoption inside your org.

IMMUTABLE RELEASES — THE QUIET FIX

Git tags (and therefore Releases) were historically mutable — an attacker could silently retarget a tag that workflows pinned. Immutable Releases makes that retarget detectable/blocked. Enable it at the org level; pair with dependency locking for end-to-end provenance.

08 / Adjacent Trend — AI / Agentic Workflows

Copilot coding agent and custom agentic workflows now trigger directly from Actions (PR review agents, release-notes automation, "agent-of-day" patterns). This trend is driving the security roadmap — agent-triggered workflows responding to issue / pull_request / discussion events are exactly the attack surface that Workflow Execution Protections + scoped secrets are designed to contain. Community tooling (e.g., gh-aw) is fast-moving but outside GitHub's core roadmap.

↓
RULESET GATE — ACTOR + EVENTOrg ruleset decides: can this actor fire this event on this workflow?
↓
SCOPED SECRET INJECTIONOnly branch/env/trusted-workflow-scoped secrets enter the job
↓
RUNNER (OUT-OF-VM FIREWALL)L7 egress enforcement outside the VM · streams telemetry to S3/Event Hub
↓
ARTIFACT + ATTESTATIONImmutable release · SLSA provenance · SBOM

11 / Failure Modes

  • Enforcing the firewall without a monitoring phase — you will deny legitimate package registries and prod endpoints. Always run Monitoring → validate allow-list → Enforcement.
  • Keeping secrets: inherit — broad inheritance defeats scoped secrets. Grep org for inherit and convert to per-secret passing.
  • Pinning top-level only — transitive Actions remain unpinned until locking ships GA. Until then, vendor composite Actions or audit their inner uses:.
  • Tag-pinning without Immutable Releases — a tag can still be retargeted. Immutable Releases + SHA+hash locking are the pair.
  • Leaving issue_comment triggers unrestricted — with agentic workflows, this is a prompt-injection channel. Gate it with Workflow Execution Protections immediately (already in preview).
Q: Which pillar should we adopt first?
A: Workflow Execution Protections (already in preview) + enable Immutable Releases today. Scoped secrets and dependency locking in preview next — enroll early. Firewall last, after a monitoring window.
