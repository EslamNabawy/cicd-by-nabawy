04 / Runners & Cost

  • Labels select runners — wrong labels = queue forever.
  • Trust — fork PRs never touch persistent self-hosted runners.
  • Cost — public free; private pool 2–3k min/mo; then ~$0.006 Linux / $0.010 Windows / $0.062 macOS. macOS burns 10×.
  • Killers — macOS builds, no cache, sprawling matrices, failed jobs bill like green ones.

05 / Power Patterns

REUSABLE (workflow_call) — one pipeline, N repos. MATRIX — fan out versions in one block. CONCURRENCY — cancel stale runs. PATHS — docs-only PRs skip CI. SETUP — drop the YAML, push, watch Actions tab, require the check in branch protection.
ARC SCALE SET ephemeral runners on your cluster, scale-to-zero idle, burst to max on PR storms. Remote caches (not pod disks). Wins when hosted minutes cost more than cluster ops.

Part 1: GitLab CI

GitLab CI is the pipeline engine inside GitLab: one YAML file in the repo (.gitlab-ci.yml) driving stages, runners, and environments — the same concepts as Jenkins and Actions, with GitLab's own vocabulary.

1. What Is It?

Picking up from GitHub Actions, where workflows lived beside the code — GitLab goes further: repo, pipeline, registry, and environments are one product, so the pipeline natively knows about merge requests, environments, and review apps.

2. Pipeline Anatomy (GitLab Vocabulary)

stages: [build, test, deploy]
build:
  stage: build
  script: [npm ci, npm run build]
test:
  stage: test
  needs: [build]          # DAG edge — runs as soon as build passes
  • Stages run in order; jobs in the same stage run in parallel.
  • needs: builds a DAG (like Actions), skipping stage waits.
  • rules: decides when jobs run (merge request only, main only, paths changed) — replaces the older only/except.
  • artifacts: passes files between jobs (reports, coverage, JUnit); cache: speeds reruns (lockfile-keyed, same discipline as everywhere).

3. Runners & Tags

Runner scopeUse
SharedFleet managed by the instance; default for most jobs
Group / project (specific)GPU, private network, compliance isolation
Tags (tags: [gpu])Route jobs to capable runners

One job = one runner by default; scale = more runners. Self-managed runners need the same patching/scaling discipline as any self-hosted fleet.

4. Environments, Review Apps & Merge Trains

  • Environments (environment: staging/production) track what's deployed where; production gates add manual approvals — the same delivery-vs-deployment line as everywhere.
  • Review apps (on_stop: teardown) spin a live environment per merge request and destroy it on merge — GitLab's built-in preview environments.
  • Merge trains serialize merges onto latest green main with re-verification — the same race the merge queue solves elsewhere.

5. GitLab vs the Sisters

GitLab CIGitHub ActionsJenkins
Config lives.gitlab-ci.yml in repo.github/workflows/Jenkinsfile in repo
RunnersShared fleet + tagsHosted + ARCController + agents
EnvironmentsBuilt-in (+ review apps)Environments as gatesManual promotion jobs
Best whenAlready on GitLab; want one productAlready on GitHubNeed total control

6. Failure Modes

  • Shared-runner queues at peak → pin critical jobs to tagged runners or add project runners.
  • rules: mis-scoping → jobs silently skip; every rules: change deserves a pipeline dry-run on a test MR.
  • Artifacts bloating storage → expire aggressively (expire_in:), keep images in the registry not in job artifacts.

7. Interview Notes

  • needs: vs stage ordering: when the DAG matters.
  • Review apps lifecycle: create on MR, destroy on merge (on_stop).
  • Merge trains: which race they eliminate.

Part 2: ArgoCD & GitOps

GitOps: git is the desired state, an in-cluster operator pulls reality toward it. ArgoCD is that operator for Kubernetes — the pipeline stops pushing to prod and starts committing to git.

1. What Is It?

Picking up from GitLab CI, where pipelines pushed artifacts outward — ArgoCD inverts the last mile: the CI pipeline builds the image and commits the new digest to a manifests repo; ArgoCD (running inside the cluster) notices and syncs. Cluster credentials never leave the cluster.

2. Push vs Pull

Push (classic CD)Pull (GitOps)
ActorExternal pipeline holds cluster credsIn-cluster agent, creds stay inside
Source of truthPipeline run historyGit commit
RollbackRedeploy old digestgit revert
DriftSilent until noticedDetected + optionally auto-healed

3. Core Objects

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: checkout }
spec:
  source: { repoURL: https://git/ops, targetRevision: main, path: apps/checkout }
  destination: { server: https://kubernetes.default.svc, namespace: prod }
  syncPolicy: { automated: { prune: true, selfHeal: true } }
  • Application: what (repo+path+revision) goes where (cluster+namespace).
  • Sync waves + hooks: order resources (CRDs before CRs, migrations before app) — the deployment strategy's sequencing, declaratively.
  • ApplicationSet: one template → N environments/tenants; preview environments become a generator, not a script.
  • Image Updater (optional): tracks new digests and commits them — automation with git as the audit trail.

4. Where It Fits

CI still builds, tests, scans, signs (everything upstream unchanged). The handoff changes: instead of kubectl apply from CI, CI commits image: sha-9f3a to the ops repo. Promotion = pull request between env branches/folders — reviewable, revertable, auditable.

5. Failure Modes

  • Auto-sync + bad commit → bad state propagates at machine speed; gate with manual sync on prod or automated kill criteria.
  • Secrets in the manifests repo → use external secret operators (External Secrets, Sealed Secrets); git holds references, never values.
  • selfHeal fighting hotfixes → emergency kubectl edits get reverted; declare a break-glass procedure (pause sync, fix, commit).
  • Monorepo scale → thousands of Applications; shard by team/cluster with ApplicationSets.

6. Interview Notes

  • Push vs pull: credential blast radius is the core argument.
  • What sync waves solve (ordering without scripts).
  • Rollback in GitOps: why git revert beats redeploy.

The Roadmap

15

Jenkins ships on cadence, not calendar — every week a new release, every four weeks a stabilized LTS, security fixes whenever they are needed. The 2026 roadmap is organized into horizons, not hard dates, because contributor bandwidth decides when an initiative ships.

01 / Release Cadence — Current Model

Unlike vendor-driven products, Jenkins never announces a "Jenkins 3.0." It evolves as a rolling train of weekly releases; the LTS line is a curated snapshot for conservative upgraders.

TrackRhythmWho should follow
WeeklyEvery week (2.545 → 2.566+ in 2026)Teams that want features fastest; accept more churn
LTSCut every ~4 weeks + backportsMost production controllers — stable, patched
SecurityAs needed via jenkinsci-advisoriesEveryone — apply out-of-band when CVE drops
2026 SHIPPED 2.545 (Jan) Java 21+ required on controller · 2.552 (Feb) experimental Plugin Manager UI + revamped Clouds page · 2.554 (Mar) script console adapted for new UI · 2.556 (Mar) Spring Security 7 + Spring Framework 7 · LTS 2.541.1 (Jan) unified RPM repo, new GPG key for RPM/DEB.

02 / How Horizons Work

RELEASED
PREVIEW
CURRENT
NEAR TERM
FUTURE

Released is done. Preview is usable but still changing. Current is under active development. Near Term is next up once bandwidth allows. Future has consensus but no active work. Treat Near/Future as directional priorities — the Jenkins project explicitly warns they are not committed dates.

READING RULE

Jenkins does not commit to delivery dates — all initiatives depend on volunteer/contributor availability. Track progress via the live roadmap.yml on GitHub, not via this snapshot.

TREATING NEAR TERM AS A COMMITMENT

The most common misread. Near/Future are priorities ordered by contributor interest, not sprint commitments. A "Near Term" label is not a quarter promise — it means "next up when someone can staff it." Plan adoption as if/when, not when.

  • Pinning automation to weekly UI screenshots — UI/UX is actively churning (Plugin Manager, Look & Feel). Gate UI automation behind CSS selectors and cache-busting, or prefer JCasC/Groovy init over scraping.
  • Ignoring the cert window — MSI DigiCert expiry May 2026 is the infra team's top priority; Windows install flows that verify publisher certs can break if you lag the migration.
  • Staying on Puppet assumptions — Puppet → Ansible is in progress. If you contribute infra or mirror infra patterns internally, expect playbook drift.
  • Assuming "Pipeline as YAML" replaces Groovy tomorrow — it's Preview. Groovy Jenkinsfile and JTE remain the production path; YAML is additive.

No. That rework has consensus but no active development. Upgrade on the LTS cadence; the incremental UI improvements (dark theme, Plugin Manager) ship steadily regardless.

Pillars A & B

21

03 / A — Locking Workflow Dependencies

A new dependencies: section in workflow YAML. Works like go.sum / Cargo.lock — but for Actions. GitHub will resolve and lock direct and transitive Action dependencies via commit SHA + cryptographic hash verification.

name: ci
on: pull_request
dependencies: # NEW — lockfile for Actions
actions/checkout: sha256:abc123…  # SHA + hash, verified
my-org/composite-action: sha256:def456…  # transitive deps locked too
jobs:
build:
runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@abc123  # deterministic, diffable
WHY THIS MATTERS Today's SHA pinning only covers top-level uses: lines, not what a composite Action calls internally. Locking closes that gap: deterministic execution, visible dependency diffs in PRs, and tamper detection even when a SHA looks correct (hash mismatch fails the run). Paired with immutable releases and stricter publishing rules for maintainers.

04 / B — Scoped Secrets

Secrets will be bindable to a narrower scope instead of flowing broadly by default — and will no longer auto-inherit into reusable workflows.

ScopeSecret is available only when
RepositoryWorkflow runs inside that specific repo
BranchWorkflow runs targeting that branch
EnvironmentJob targets the environment (e.g., production)
Trusted workflowOnly an explicitly approved reusable workflow calls it
# BEFORE — secrets auto-inherit
jobs:
deploy:
uses: org/central-deploy@v2
    secrets: inherit               # ← broad, implicit
# AFTER — explicit per-secret binding
jobs:
deploy:
uses: org/central-deploy@v2
    secrets:
NPM_TOKEN: ${{ secrets.NPM_TOKEN }}  # scoped to trusted workflow + env
PERMISSION CHANGE Repository write access will no longer automatically grant secret-management rights. That moves to custom/delegated roles (separation of duties). Treat secrets: inherit as deprecated — audit for it now.

05 / C — Policy-Driven Workflow Execution Protections

Extends the existing rulesets framework to centrally govern workflow execution — replacing scattered if: github.actor != 'dependabot[bot]' guards spread across individual workflow files.

Rule typePurposeExample
Actor rulesWho/what can trigger workflowsOnly humans, Dependabot, or a specific GitHub App can fire deploy.yml
Event rulesWhich events can trigger runspush allowed; issue_comment blocked unless from maintainer
DIRECTLY TARGETS "COMMENT-AND-CONTROL"

Untrusted contributors trigger agent/automation workflows via issue or PR comments, injecting instructions into AI-assisted runs. Central policy prevents the trigger from ever reaching the runner — no per-workflow patching needed. Status: Public preview shipped June 18, 2026.

# org-level ruleset (conceptual)
ruleset: workflow-execution
  target: workflows
  conditions:
actor: [human, dependabot[bot], my-deploy-app]
    event: [push, pull_request, workflow_dispatch]
  # issue_comment / discussion events require actor allow-list

06 / D — Endpoint Monitoring & Control

Actions data stream — near-real-time telemetry for workflow runs, streamed to Amazon S3 or Azure Event Hub / Data Explorer. Designed for SIEM/SOC consumption.

  • Workflow execution metadata — status, duration, runner type
  • Dependency-resolution detail — which Action resolved to which version
  • Network activity — planned; feeds the firewall policy workflow

Native egress firewall (Layer 7) — runs outside the GitHub-hosted runner VM, so code inside the runner cannot bypass it.

ModeBehaviorUse when
MonitoringLogs all outbound trafficBuilding your allow-list without breakage
EnforcementBlocks requests outside the allow-listAfter allow-list is validated in monitoring
ROLLOUT DESIGN Two-mode rollout is intentional: run in Monitoring to discover destinations, cut to Enforcement only when vetted. This is how GitHub avoids "enforcement day breaks every CI" — mirror the same staged adoption inside your org.

Decision Framework

29

05 / Choose Jenkins When

  • You need on-prem / air-gapped execution (regulated, government, no egress).
  • Build/deploy logic is highly custom, heterogeneous, or legacy — multiple SCMs, mixed Windows/Linux/mainframe, non-GitHub source.
  • You have deep Jenkins/Groovy expertise and migration cost outweighs benefit.
  • You need very fine-grained control over execution engine, distributed builds, custom scheduling.
  • Cost model must be zero marginal cost per build minute (owned hardware).

06 / Choose GitHub Actions When

  • Source already lives on GitHub — single strongest signal; PR/Issues/Checks integration is hard to replicate.
  • You want low-maintenance SaaS CI with minimal infra ownership.
  • You value a large, fresh Marketplace ecosystem and fast onboarding (YAML simpler than Groovy for most teams).
  • You want the newest supply-chain security defaults (locking, scoped secrets, egress firewall) as they roll out in 2026.
  • You are building agentic / Copilot-assisted workflows and want native platform support.

07 / Consider Both Together (Common in Larger Orgs)

MIGRATING — Run legacy jobs on Jenkins while new services onboard to Actions. SPECIALIZED — Jenkins for on-prem workloads (hardware-in-the-loop, mainframe) while Actions handles standard app CI. ORCHESTRATED — Actions as the trigger/orchestration layer (PR gating, release tagging) calling Jenkins as a specialized executor via webhook/API.
# hybrid topology (conceptual)
PR / push → GitHub Actions (lint, test, gate) → if specialized →
  webhook → Jenkins controller (hardware-in-the-loop, mainframe, air-gapped build)
        ↘ else → Actions runners (build, SBOM, deploy to cloud)
# two systems, one lifecycle: SOURCE → PIPELINE → VALIDATION → ARTIFACT → RELEASE

11 / Failure Modes — Decision Edition

MIGRATING FOR THE ROADMAP INSTEAD OF YOUR CONSTRAINTS

The most expensive mistake: moving a working Jenkins estate to Actions (or vice versa) because a roadmap looks shinier, without scoring your actual constraints — air-gap, legacy SCM, secret posture, team skill, cost at volume. Score the gut-check table first; only migrate where the signal is clear.

Only if you score high on the Actions signals (code on GitHub, SaaS desire, supply-chain defaults, agentic work) or need a hybrid split (Actions gates standard app CI, Jenkins keeps specialized builds). Otherwise, invest in the Jenkins modernization path — LTS hygiene, JCasC, Script Security.

Push: external pipeline holds cluster creds. Pull: in-cluster agent syncs from git, creds stay inside.
Q3 Why does git revert beat redeploy for GitOps rollback?

Revert is reviewable, revertable and auditable — history stays the source of truth.
Q4 Which race do merge trains eliminate?

Green-on-branch-red-on-main: every merge re-verified against latest green main.
Q5 Which roadmap pillar first?

Workflow Execution Protections (in preview) plus Immutable Releases today. Firewall last.
Q6 Monitoring before Enforcement — why?

Enforcement without a validated allow-list denies real registries and endpoints.
Q7 Pipeline as YAML vs Groovy?

YAML is additive Preview for teams preferring it. Groovy Jenkinsfile stays the production path.
Q8 Strongest single signal for Actions?

Source already on GitHub — PR, Issues and Checks integration is hard to replicate.
